# Animation transport bar layout — design

**Date:** 2026-08-07
**Status:** Approved

## Problem

The animation transport bar (`.pf-anim-bar`, generated by
`animation-controls.js`) floats centered at the bottom of the stage; the
viewbar (`#viewbar`, `.pf-float-viewbar` — cutaway/reframe/theme buttons)
floats at the stage's bottom-right. Two defects:

1. **Height mismatch.** The transport bar (~36px) is visibly shorter than the
   viewbar card (44px) sitting on the same bottom edge.
2. **Overlap.** Nothing stops the centered transport bar from sliding under
   the viewbar when the stage narrows (wide layout, rail expanded). Above the
   narrow breakpoint both sit in the same bottom band at `z-index: 15`.

## Requirements

- The transport bar's card must never be shorter than the viewbar card.
- The two cards must never overlap; a gap of **at least 10px** must always
  separate them.
- The transport bar stays truly centered in the stage whenever there is room,
  and **slides left** (not merely shrinks) when there isn't. It never crosses
  the stage's 12px left margin; if it still can't fit at the leftmost
  position, its width is capped so the 10px gap holds.
- The narrow layout (≤719px), where the bar already sits *above* the viewbar
  at `bottom: 64px`, must be unaffected — the constraint applies only when
  the two bars' vertical bands actually intersect.

## Approach (chosen from four candidates)

**JS measure-and-clamp.** Pure CSS cannot express "centered until colliding
with a sibling of unknown width" without either hard-coded worst-case
constants (bar sits permanently off-center), anchor positioning (no Firefox),
or restructuring `#viewbar` into a shared grid container (breaks the
partforge-cloud host re-anchoring contract documented in chrome.css). A small
measured clamp gives exact behavior in every browser without touching host
markup.

## Design

### 1. Height match — pure CSS (`app.css`)

- `.pf-anim-bar { min-height: 44px; box-sizing: border-box; }` — 44px is the
  viewbar's rendered height (34px button + 2×4px padding + 2×1px border),
  documented in a comment the same way chrome.css's narrow-layout
  `bottom: 64px` rule derives from the same math.
- The existing `@media (max-width: 360px)` block that shrinks the viewbar to
  40px (30px buttons) gets a matching `min-height: 40px` override.

### 2. Collision avoidance — pure function + ResizeObserver wiring

**Pure function** (exported from `animation-controls.js`, unit-testable):
takes the stage width, the bar's natural (unconstrained) width, and the
viewbar's rect relative to the stage (or `null` when absent/not vertically
intersecting), plus constants `GAP = 10`, `MARGIN = 12`. Returns either
"centered" (no override) or `{ left, maxWidth? }`:

- `centeredLeft = (stageWidth − barWidth) / 2`
- `limit = viewbarLeft − GAP − barWidth`
- centered when `centeredLeft ≤ limit`; otherwise `left = max(MARGIN, limit)`
- when even `left = MARGIN` doesn't fit,
  `maxWidth = viewbarLeft − GAP − MARGIN` caps the bar.

**Wiring** (inside `attachAnimationControls`): a `ResizeObserver` on the
stage, the bar, and the viewbar (viewbar size changes when cutaway's
Flip/Reset actions appear). On each notification, measure
`getBoundingClientRect()` of bar and viewbar relative to the stage; apply the
constraint **only if the two rects' vertical ranges intersect** (this is what
exempts the narrow layout and any host re-anchoring that separates them).
Constrained: set inline `left`, neutralize the CSS `transform` centering, set
`max-width`. Unconstrained: clear all inline overrides so chrome.css stays
authoritative. Natural bar width is measured with overrides cleared (or via
`scrollWidth`) so the clamp doesn't feed back on itself. Observer is
disconnected in the existing teardown path.

Viewbar lookup: `#viewbar` within the mounted app root; when absent the bar
stays centered.

### 3. Testing

- **Unit (vitest):** the pure placement function — centered with room,
  slide-left at collision, clamp at left margin, max-width cap when
  oversized, no-op when rects don't vertically intersect.
- **Real browser (`scripts/check-app.mjs`, hinged-box.html):** assert the
  transport bar and viewbar rects never overlap and keep the ≥10px gap, both
  at the default viewport and at a squeezed width chosen so the centered
  position *would* collide (proving the slide-left path fires); assert the
  transport bar's rendered height is ≥ the viewbar's.

## Out of scope

- The narrow-layout (≤719px) stacking of the bar above the viewbar stays
  as-is.
- No changes to `#viewbar` markup, placement, or the host re-anchoring
  contract.
